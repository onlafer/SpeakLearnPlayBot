# Pre-Server Testing

Этот файл описывает удобную схему проверки бота перед переносом на сервер без постоянной правки `config/.env`.

## Короткий ответ

Для повседневной проверки не нужна временная VM.

Лучше использовать 3 уровня:

1. `quick` локально: быстро проверить конфиг, импорты и БД.
2. `models` локально: дополнительно проверить тяжелые модели и `Ollama`.
3. `full` перед выкладкой: проверить все то же самое плюс доступ к Telegram API.

Временную Linux VM или VPS имеет смысл поднимать только для финального прогона, если важна близость к боевому окружению:

- другой Linux-дистрибутив;
- другая версия CUDA;
- другая видеокарта;
- другая схема хранения моделей.

## Почему не VM на каждый запуск

У проекта есть тяжелые компоненты:

- `faster-whisper`;
- `F5-TTS`;
- `ruaccent`;
- локальный `Ollama`.

Если каждый раз поднимать пустую временную VM, вы будете заново тратить время на:

- установку зависимостей;
- прогрев моделей;
- скачивание весов;
- проверку `ffmpeg`, `torch`, `onnx`, `cuda`.

Это неудобно и дорого по времени.

Намного практичнее:

- держать основной цикл проверки локально;
- хранить модели в постоянных каталогах;
- использовать временную VM только как финальный smoke-test перед продом.

## Что уже добавлено в проект

Добавлены два служебных скрипта:

- [scripts/run_with_env.py](../scripts/run_with_env.py)
- [scripts/smoke_check.py](../scripts/smoke_check.py)

Они решают две основные проблемы:

1. Можно запускать бот или API с любым `.env`, не переписывая `config/.env`.
2. Можно делать быстрые предсерверные проверки по профилям.

## Рекомендуемая схема окружений

Рекомендуется завести три файла:

- `config/.env.local`
- `config/.env.smoke`
- `config/.env.prod`

Пример создания тестового файла:

```powershell
Copy-Item config/.env.example config/.env.smoke
```

Идея такая:

- `.env.local` для обычной разработки;
- `.env.smoke` для предсерверной проверки;
- `.env.prod` как шаблон для боевого сервера.

## Быстрые проверки

### 1. Быстрая проверка проекта

Проверяет:

- наличие `.env`;
- обязательные переменные;
- импорты Python;
- подключение к БД.

```powershell
uv run python scripts/smoke_check.py --env-file config/.env.smoke --profile quick
```

### 2. Проверка моделей

Проверяет:

- все из `quick`;
- наличие файлов `F5-TTS`;
- загрузку `Whisper`;
- тестовый прогон `F5-TTS`;
- доступность `Ollama`.

```powershell
uv run python scripts/smoke_check.py --env-file config/.env.smoke --profile models
```

### 3. Полная проверка перед сервером

Проверяет:

- все из `models`;
- валидность токена через Telegram API.

```powershell
uv run python scripts/smoke_check.py --env-file config/.env.smoke --profile full
```

## Запуск бота с нужным `.env`

Теперь можно запускать любые команды с выбранным env-файлом.

### Бот

```powershell
uv run python scripts/run_with_env.py --env-file config/.env.smoke -- uv run main.py
```

### API

```powershell
uv run python scripts/run_with_env.py --env-file config/.env.smoke -- uv run python -m api.main
```

### Проверка БД

```powershell
uv run python scripts/run_with_env.py --env-file config/.env.smoke -- uv run python -m scripts.check_db_connection
```

## Важное замечание про `run_local.py`

Текущий [run_local.py](../run_local.py) автоматически обновляет `WEBAPP_URL` внутри `config/.env`.

Это удобно для обычной локальной работы, но не очень удобно для изолированного smoke-окружения, потому что:

- он изменяет файл;
- он завязан именно на `config/.env`;
- он поднимает сразу несколько процессов.

Поэтому для предсерверной проверки лучше использовать:

- `scripts/smoke_check.py` для проверок;
- `scripts/run_with_env.py` для точечных запусков.

## Как работать с большим количеством моделей

Если моделей много, лучший вариант такой:

1. Не запекать веса внутрь каждой временной VM.
2. Хранить модели в постоянном каталоге или постоянном volume.
3. Проверять код отдельно от проверки моделей.
4. Тяжелую проверку моделей запускать только перед выкладкой или после изменения ML-части.

Практически это выглядит так:

- на каждом изменении гонять `quick`;
- перед релизом гонять `models`;
- перед переносом на сервер гонять `full`;
- на временной VM запускать только финальный контрольный прогон.

## Когда временная VM действительно нужна

Поднимайте временную VM, если хотите проверить именно боевую совместимость:

- Linux вместо Windows;
- CPU-only режим вместо локальной GPU;
- другую версию CUDA;
- отдельный сервер с `Ollama`;
- внешний PostgreSQL вместо локального SQLite.

В таком случае хороший сценарий такой:

1. Поднять VM.
2. Развернуть код.
3. Подключить или заранее прогреть каталог с моделями.
4. Запустить `smoke_check.py --profile full`.
5. Если все прошло, переносить на основной сервер.
6. VM удалить.

## Практическая рекомендация для этого проекта

Для вашего бота я бы рекомендовал такой рабочий процесс:

1. Разработка на локальной машине.
2. Проверка `quick` после обычных изменений.
3. Проверка `models` перед релизом.
4. Один финальный прогон на временной Linux VM только если нужна проверка окружения, похожего на сервер.

То есть VM нужна не как основной способ разработки, а как последний этап подтверждения.
